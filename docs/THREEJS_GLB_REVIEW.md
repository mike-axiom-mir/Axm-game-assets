# Three.js verified GLB review stage

This lane closes one experience/evidence gap after verified rigid GLB delivery: a human can now load the exact admitted GLB through a pinned local Three.js runtime and inspect the real engine realization instead of stopping at structural JSON/GLB compatibility evidence.

## Why this is separate from the diagnostic review board

The existing diagnostic review board presents AXM-native silhouette, depth and normal software-raster signals. Those are useful truth/diagnostic views, but they deliberately are **not** Godot/Three.js/Unreal rendering.

This stage owns a different downstream question:

> Does this exact verified GLB actually load and present coherently through the intended Three.js consumer stack, and can a human inspect that realization without confusing it with visual approval or canonical state?

The stage does not replace the diagnostic board and does not create another asset truth source.

## Build

Provide:

- one GLB generated by `native_glb_delivery.py`;
- that delivery's exact JSON receipt;
- a caller-selected local Three.js package root;
- the exact Three.js version expected by the caller.

Example:

```bash
python threejs_glb_review.py \
  --glb build/northpole-guard-review-proxy.glb \
  --delivery-receipt build/delivery-receipt.json \
  --three-root node_modules/three \
  --expected-three-version 0.180.0 \
  --output-dir build/threejs-review
```

The builder rejects altered GLB bytes, widened delivery authority, incompatible rigid-delivery truth, a mismatched Three.js package/version, and missing runtime modules/license before emitting the review stage.

## Local/offline runtime boundary

The generated stage copies only the bounded local runtime pieces it needs:

- `build/three.module.js`;
- `examples/jsm/loaders/GLTFLoader.js`;
- `examples/jsm/controls/OrbitControls.js`;
- `examples/jsm/utils/BufferGeometryUtils.js`;
- the Three.js `LICENSE`.

Their SHA-256 identities are recorded in `review-receipt.json`. After the stage is built, the page contains no CDN or network URL. Serve the output directory with a local static server, for example:

```bash
python -m http.server 8080 --directory build/threejs-review
```

Then open `http://127.0.0.1:8080/`.

The local HTTP server is only a browser module-loading mechanism. The stage does not contact a cloud service, account, model, relay, package registry or external asset host after it has been built.

## Human loop

The real Three.js surface provides:

- GLTFLoader admission of the exact copied `asset.glb`;
- orbit/zoom inspection;
- explicit left/right rotation controls;
- wireframe toggle;
- reset view;
- keyboard rotation/reset/wireframe controls;
- mesh, triangle, bounds and live draw-call readback;
- exact GLB/source-manifest/consumer-request identities;
- expandable delivery and engine-stage receipts;
- a visible render/HELD status.

Phone realization keeps the same evidence and ≥44 px controls rather than hiding the truth rail.

## Truth ceiling

A generated `review-receipt.json` says `browser_render_observed: false`. Stage generation cannot truthfully claim that a browser actually rendered the asset.

The hosted Experience witness separately loads the generated stage in Chromium and requires the page to publish a post-GLTFLoader render witness with:

- the expected Three.js revision;
- at least one mesh and triangle;
- live draw calls;
- the exact delivery SHA-256;
- unchanged all-false adoption/approval/merge/CANON authority.

Even that browser PASS proves only a bounded engine realization. It does **not** prove:

- final Northpole Guard visual quality;
- character semantics, skeleton, skinning or animation;
- collision/gameplay fitness;
- production performance acceptance;
- engine/runtime adoption;
- visual approval;
- release, merge or CANON.

The current proving GLB is explicitly a rigid proxy used to exercise delivery and review plumbing. A useful engine screenshot is evidence, not automatic aesthetic promotion.
